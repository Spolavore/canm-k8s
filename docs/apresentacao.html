CANM

Cost-Aware Node Migration

Otimização de custos em Kubernetes via migração de nós orientada a métricas de utilização


GKE  ·  TypeScript  ·  Prometheus  ·  FinOps


TCC · Econodata Platform Engineering

O Problema

Clusters Kubernetes são frequentemente dimensionados para o pico de carga, mas ficam ociosos por grande parte do dia.


☀️ Horário de pico

  • Alta demanda de CPU e memória
  • Nós N2 (alta performance) justificados
  • Custo elevado necessário

🌙 Horário ocioso

  • Score de utilização cai abaixo do threshold
  • Nós N2 continuam rodando
  • Custo elevado desnecessário

💡 Uma máquina E2 custa cerca de 40–60% menos que uma N2 equivalente no GKE.

A Proposta: CANM

Um agente autônomo que migra nós entre node pools reativamente a métricas de utilização — respondendo ao desperdício de recurso antes que ele se acumule em custo.

Arquitetura: 3 Componentes

📊 MetricsAdapter

  • Consulta o Prometheus
  • CPU, memória e rede por nó
  • Calcula score ponderado
  • Pesos configuráveis

🔧 GkeNodeMigrator

  • Adiciona nó no pool destino
  • kubectl drain no nó origem
  • Remove nó via MIG (gcloud)
  • Retorna bool de sucesso

🎛️ MigratorOrchestrator

  • Loop contínuo (padrão: 1 min)
  • Avalia scores vs. thresholds
  • Aplica política de migração
  • Controla cooldown

📝 AuditLogger

Persiste cada migração em migrations.jsonl — timestamp, duração, direção, score, pool origem/destino, política e status de sucesso. Formato otimizado para análise com pandas.

Score de Utilização por Nó

Cada nó recebe um score composto calculado a partir de três métricas do Prometheus:

score = (cpu_usage × w_cpu) + (mem_usage × w_mem) + (net_bytes × w_net)

MétricaUnidadePeso padrãoEnv var
CPU usage%0.60CPU_WEIGHT
Memory usage%0.30MEMORY_WEIGHT
Network receivedMB0.10NETWORK_WEIGHT

Score baixo → nó ocioso → candidato a migrar para pool barato (E2)
Score alto  → nó sob carga → candidato a migrar para pool rápido (N2)

Lógica de Decisão

A cada ciclo (checkInterval), o orquestrador avalia os nós de ambos os pools:


🟢 prioritizeCost padrão

  1. Se score de nó N2 ≤ lowScoreThreshold → migra para E2
  2. Caso contrário, se score de nó E2 ≥ highScoreThreshold → migra para N2

Prioridade: economizar custo

🔴 prioritizePerformance

  1. Se score de nó E2 ≥ highScoreThreshold → migra para N2
  2. Caso contrário, se score de nó N2 ≤ lowScoreThreshold → migra para E2

Prioridade: garantir performance


Uma migração por ciclo, nó a nó — evita sobrecarga no cluster durante a transição.

CANM · TCC

Anti-Thrashing: Cooldown

Sem cooldown, o orquestrador poderia migrar um nó de volta imediatamente após uma migração — gerando loops caros e instáveis.


⏱️ Como funciona

Após uma migração, o nó novo entra em período de cooldown baseado no seu creationTimestamp na GCE. Enquanto o nó estiver dentro da janela, ele é ignorado na avaliação.

⚙️ Configuração

PoolPadrãoEnv var
N2 (high)30 minHIGH_NODE_COOL_DOWN
E2 (low)5 minLOW_NODE_COOL_DOWN

Aceita unidades: 30m, 1h, 3600s


O N2 tem cooldown maior porque o resize de node pool via gcloud é uma operação mais lenta e cara.

CANM · TCC

O que o CANM garante

✅Migração automática baseada em métricas — score composto de CPU, memória e rede, com pesos configuráveis.

✅Anti-thrashing por cooldown — nenhum nó é reavaliado antes de sua janela de cooldown expirar.

✅Migração nó a nó — um nó por ciclo, reduzindo impacto simultâneo no cluster.

✅Rastreabilidade completa — cada migração é registrada no audit log JSONL com timestamp, duração, direção, score e status.

✅Drain respeitando o Kubernetes — usa kubectl drain --ignore-daemonsets --delete-emptydir-data, aguardando o rescheduling dos pods.

✅Configuração totalmente via env vars — sem necessidade de rebuild para ajustar thresholds, pesos ou política.

CANM · TCC

O que o CANM não garante

❌Zero downtime por si só — o drain evita interrupção brusca, mas zero downtime real depende de mecanismos da aplicação: PodDisruptionBudget, múltiplas réplicas e graceful shutdown configurados pelo time de engenharia.

❌Estado do Redis — pods com estado (Redis sem persistência) podem perder dados durante o drain se não houver replicação ou snapshot prévio. O CANM não orquestra persistência de estado.

❌Economia garantida em R$ — a migração para E2 é uma condição necessária, mas a economia real depende do tempo acumulado em cada pool. O CANM registra os dados; a análise de custo é feita externamente.

❌Disponibilidade durante falhas de infraestrutura — se o gcloud resize falhar (quota, permissão, timeout), a migração é abortada. Não há retry automático implementado.

CANM · TCC

Pré-requisitos para Zero Downtime

O CANM usa kubectl drain que respeita PDBs — mas a responsabilidade de configurá-los é da aplicação.


Responsabilidade da aplicação

  • PodDisruptionBudget com minAvailable ≥ 1
  • Mínimo de 2 réplicas por serviço crítico
  • Graceful shutdown (terminationGracePeriodSeconds)
  • Redis com replicação ou persistência habilitada

Responsabilidade do CANM

  • Invocar drain com --grace-period=60
  • Aguardar o novo nó estar Ready antes de drenar
  • Migrar um nó por vez
  • Registrar sucesso/falha no audit log

Exemplo de PDB adequado:

apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: backend
